# PLSM固定框架代理兼容（2026-11-12）

## 本次约束与调整

用户确认主框架代理、子应用注册、平台功能配置全部维持现场现状。本次只修改PLSM容器Nginx，不修改主框架或平台配置。端口仍为29876，项目入口仍为 `http://10.151.255.167:18090/sub/plsm/`。

截图中的主框架配置为：

```js
'/sub/plsm': {
  target: 'http://localhost:29876/sub/plsm',
  ws: false,
  changeOrigin: true,
  rewrite: path => path.replace(/^\/sub\/expense/, ''),
}
```

该rewrite不能去掉PLSM请求的前缀；若运行时代理将target路径与请求路径拼接，上游会收到 `/sub/plsm/sub/plsm/…`。本次在容器内增加精确兼容规则，将双前缀内部改写为单前缀，再交给原有静态资源和history回退规则。无需移动页面源码或改变构建PUBLIC_PATH；正常单前缀请求仍可用。

| 容器收到的请求 | 实际处理路径 |
|---|---|
| /sub/plsm/ | /sub/plsm/ |
| /sub/plsm/sub/plsm/ | /sub/plsm/ |
| /sub/plsm/sub/plsm/js/实际分包.js | /sub/plsm/js/实际分包.js |
| /sub/plsm/sub/plsm/plsm-release.json | /sub/plsm/plsm-release.json |
| /sub/plsm/sub/plsm/plsmSerialPart | /sub/plsm/plsmSerialPart，回退子应用index |

这是内部改写，不向浏览器返回跳转，不改变地址栏或微应用基座；查询参数保留。缺失JS/CSS仍返回404，HTML及发布标识仍禁缓存，不会把HTML伪装成成功的JS响应。规则只兼容PLSM双前缀，不为其他微应用或任意根路径提供页面。

## 发布方法

1. 在上一交付版本469915a上合并本次源码变更包，内网仍使用test分支及原来的 `yarn build:test` 流程。
2. Dockerfile和静态目录保持既有配置：dist复制到 `/usr/share/nginx/html/sub/plsm/`，镜像使用完整的 `deploy/nginx.release.conf`。
3. **如果发布单挂载Nginx配置，必须将内容替换为本次完整的 `deploy/nginx.release.conf`，挂载路径为 `/etc/nginx/nginx.conf`。** 只更新镜像而保留旧挂载，会覆盖本次兼容规则。分文件方式则使用根nginx.conf和本次deploy/nginx.conf。
4. 服务、容器和三项健康检查端口保持29876，不增加80监听。主框架保持用户截图中的配置，不要求改代理或注册。

先通过可达的29876服务地址分别请求 `/sub/plsm/plsm-release.json` 和 `/sub/plsm/sub/plsm/plsm-release.json`，两者应返回相同JSON且状态200。再请求 `http://10.151.255.167:18090/sub/plsm/plsm-release.json`，应与直连结果一致。随机不存在的 `.js` 路径应返回404。

然后在主平台点击PLSM菜单，查看Network是否实际加载了 `/sub/plsm/` 下的HTML与JS。只测试静态地址成功，不代表菜单和API已经联调通过。

## 子应用无法接管的边界

用户提供的 `_2026_07_32_js.txt` 是主框架的 `webpackChunkbase` 产物。其菜单逻辑先按功能路径第一段查找已注册微应用；匹配后才打开微应用，否则从主框架自己的views映射加载组件。提供的这份JS中没有plsm注册，截图中的源码已有plsm注册；两者是否对应同一次现场发布尚未确认。

因此，如果报错仍来自主框架的 `Cannot find module './plsm/serial-part/index.vue'`，且Network中没有子应用入口请求，错误发生在PLSM代码执行之前。本次Nginx兼容无法修改主框架已加载的组件映射，也不能使其跳过菜单判断；不能宣称仅部署本包就一定消除该错误。

关于旧菜单说明的更正：`/plsmSerialPart`、`/plsmVehicleQuery` 是本子应用内部功能路径。在提供的主框架JS中，对应的主框架功能路径需具有 `/plsm/` 第一段，即 `/plsm/plsmSerialPart`、`/plsm/plsmVehicleQuery`，主框架再剥离这层前缀注入子应用；它与静态入口 `/sub/plsm/` 不是同一前缀。本次按用户要求不修改现场菜单，保留该差异作为诊断依据，不创建固定路由绕过授权。

另外，截图中的localhost指主框架代理所在环境。若18090端收到502且容器没有请求，需核对现有网络转发是否能到达29876；修改子应用静态路径不能解决上游连接失败。

内部改写行为参考[Nginx官方rewrite文档](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#rewrite)。本地验证与现场验收分别记录，不把本机测试等同于内网部署成功。
