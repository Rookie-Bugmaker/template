# PLSM 角色、菜单及前端部署

本前端在 `plsm` 分支增量开发，复用模板登录、请求、动态菜单、Ant Design Vue。菜单清单参照全员业绩量化考核的配置形式；不复制其 Element Plus 或业务权限规则。

## 首次接入：项目入口与微前端

平台“项目管理 → PLSM项目 → 编辑”填写如下信息；已有后端项目时直接补入口，不重复创建第二个项目。

| 配置项 | 填写值 | 说明 |
| --- | --- | --- |
| 项目名称/编码 `name` | `plsm` | 与本次两套环境变量及请求头 `X-Project-Code` 一致，注意大小写；如果既有项目编码不同，先同步两套PROJECT_CODE，不能另建项目造成权限分离 |
| 项目中文名称 | 太初平台全寿命周期管理 | 展示名称 |
| 项目入口URL `url` | `http://10.151.255.167:18090/sub/plsm/` | 保留末尾 `/`；不填API路径、功能路径或 `#/` |
| 微前端 `microFlag` | `Y`（是） | 使用平台微前端加载；如果旧项目编辑页不显示此项，在平台支持该字段的项目配置入口维护，不能仅因保存URL成功就认定微前端标记已生效 |
| 项目状态 | 可用 | 已核对平台项目状态：`0=可用、1=禁用`，与档案生效字典不同 |
| 项目分组、图标 | 按现有业务分组选择，图标可选 `ApartmentOutlined` | 通过平台图标选择器选择，避免手填不支持的图标 |

当前模板使用 `@micro-zoe/micro-app`，无需改为qiankun。路由已优先读取主平台注入的 `__MICRO_APP_BASE_ROUTE__`；资源路径沿用 `public-path.ts` 的微应用注入机制。主平台须传入 `currentUser` 与当前角色获准的 `appFunctions`，子应用按平台功能生成路由；不要在PLSM里硬编码全部功能来绕开授权。微前端加载URL是上表项目入口，打开哪个页面由功能的“访问路径”决定。

代码已将Vue CLI/Vite的PUBLIC_PATH统一为 `/sub/plsm/`，PROJECT_CODE统一为 `plsm`，修改各环境标题，Webpack异步分包标识改为独立的 `plsm`。生产/测试构建的普通API与菜单SSE均走同源 `/api`，避免继续访问模板旧测试服务器。前端入口与后端网关服务前缀分别配置，不能把 `/sub/plsm/` 当作后端服务前缀。

## 平台角色

| 角色编码 | 角色名称 | 业务权限 |
| --- | --- | --- |
| PLSM_ADMIN | PLSM管理员 | 全项目查询、历史、导出、档案登记/制造信息修改/失效/恢复，以及已有管理入口 |
| PLSM_USER | PLSM普通用户 | 全项目查询、档案查看、历史、导出；无写入、删除、导入及同步重发 |

全项目仍受平台租户隔离。角色须在平台正式创建并分配给相应账号，本次不编造平台角色表SQL。当前所选角色由后端认证服务核对；前端权限接口只控制按钮展示，不能代替后端鉴权。外部系统使用自己的平台系统账号及后端名单，不分配PLSM人员管理员来绕过接口身份检查。

## 动态菜单清单

| 功能名称 | 功能编码 | 路径 | 组件路径 | 路由名称 | 角色 | 前提 |
| --- | --- | --- | --- | --- | --- | --- |
| 实车序列号查询 | plsm_vehicle_query | /plsmVehicleQuery | plsm/vehicle/index | PlsmVehicleQuery | 两角色 | 后端视图、查询接口、平台WkDataAPi |
| 序列号物料档案 | plsm_serial_part | /plsmSerialPart | plsm/serial-part/index | PlsmSerialPart | 两角色 | 档案表及接口；仅管理员显示维护按钮 |

组件路径相对 `src/views` 且不加 `.vue`，沿用 `generator-routers.ts` 加载；不新增硬编码静态菜单绕开平台功能授权。历史属于弹窗，无独立菜单；批次状态只建表，清单类型及数据中心报表本期不配置。

### 第一步：在功能管理登记页面

参照全员业绩量化考核“功能名称、功能编码、访问路径、前端组件、路由名称”的五字段规则，分别新建上表两项功能，所属项目均选PLSM。编码、路径、路由名称保持全局唯一；第一次配置可以直接逐字填写上表。

两项功能的其他字段统一填写：

| 字段 | 值 |
| --- | --- |
| 功能类型 `functionType` | 功能（`A`），不是按钮B或列C |
| 上级功能 | 根级/无；不要将一个页面设成另一个页面的子功能 |
| 打开方式 `openMethod` | 内部（`0`） |
| 功能参数 `parameters` | 留空，不填工厂、物料号或角色编码 |
| 重定向 `redirect` | 留空 |
| 菜单隐藏/子菜单隐藏 | 均关闭 |
| 缓存页面 `keepAlive` | 首次接入建议关闭，角色切换后重新获取页面权限 |
| 固定标签 `lockInTab`、合并标签 `mergeTab` | 均关闭 |
| 低代码页面/值集等 | 留空，使用代码组件 |

若组件编辑框自带 `@/views/` 与 `.vue`，只填写表内 `plsm/vehicle/index` 或 `plsm/serial-part/index`。访问路径只填 `/plsmVehicleQuery` 或 `/plsmSerialPart`，不能填写完整URL，不能加 `/sub/plsm`，不能加查询参数。

### 第二步：在菜单管理挂载功能

功能登记不会自动生成用户菜单。选择PLSM项目建立根菜单，再新增两个叶子菜单，绑定第一步保存的功能。

| 层级 | 菜单名称 | 建议菜单编码 | 排序 | 绑定功能 |
| --- | --- | --- | --- | --- |
| 根目录 | 太初平台全寿命周期管理 | plsm_root | 10 | 不绑定功能，作为目录 |
| 根目录下 | 实车序列号查询 | plsm_vehicle_menu | 10 | `plsm_vehicle_query` |
| 根目录下 | 序列号物料档案 | plsm_serial_part_menu | 20 | `plsm_serial_part` |

目录通过平台菜单树维护，不填写虚构的前端组件。两个叶子选择“功能”并绑定真实功能ID，不选子菜单引用 `childId`；菜单名称允许按业务习惯调整，功能五字段保持上表值。若平台已有PLSM根菜单，直接在其下挂载，不新建重复目录。实际页面路径来自功能，不是菜单编码。

### 第三步：分配角色、菜单和项目访问权限

1. 在角色管理创建或复用 `PLSM_ADMIN`、`PLSM_USER`，按平台要求关联项目、组织及人员。已有角色不重复创建。为需要进入PLSM的人员开通项目访问权限。
2. 两角色均授权 `plsm_root` 目录及其两个叶子菜单、对应两项功能；如平台以根菜单作为角色菜单入口，则将该根菜单配置给两角色，并核对叶子功能均已授权。
3. 普通用户可以查询、历史、导出；档案页面维护按钮由后端 `/plsm/permissions` 返回的 `canMaintain` 控制，写入仍由后端实时校验。当前没有新增需要人工登记的B类按钮编码，不要编造按钮码以为可以赋予写权限。
4. 如果现网另启用“功能绑定API”白名单，两角色允许：`GET /plsm/permissions`、`POST /plsm/vehicles/page`、`POST /plsm/vehicles/export`、`POST /plsm/archives/page`、`GET /plsm/history`；仅管理员允许 `POST /plsm/archives/save`。这些是后端相对路径，平台服务前缀按实际网关填写。外部系统档案接口不绑定给普通人员角色。
5. 退出重登或切换当前角色后验证。多个角色按当前选择角色判断，不合并全部角色权限；普通用户即使手工发保存请求也必须被后端拒绝。

## 前端配置与行为

- 已按用户确认在 `.env` 设置 `VUE_APP_PLSM_SERVICE_PREFIX=/workplace-plsm`、`VITE_APP_PLSM_SERVICE_PREFIX=/workplace-plsm`；开发、测试、正式构建均继承。API基础地址使用同源 `/api`，项目头为 `plsm`。不要在本地覆盖文件中保留模板的旧值，也不要将服务前缀重复拼入API基础地址。
- 完整请求示例：实车查询 `http://10.151.255.167:18090/api/workplace-plsm/plsm/vehicles/page`，档案查询 `/api/workplace-plsm/plsm/archives/page`，权限查询 `/api/workplace-plsm/plsm/permissions`。其中 `/api` 是入口代理前缀，`/workplace-plsm` 是已确认的网关服务前缀，后面的 `/plsm` 是后端Controller路径，三段各出现一次；网关转发到PLSM服务后应保留Controller的 `/plsm/...`。
- 本地构建仍使用 `yarn build:test` 或 `yarn build:production`；本机没有yarn可执行文件时使用同脚本的node命令验证，不替换锁文件、不重新安装缺失的私有链接包。
- 查询必须填写车型和车组编号；项目、产品编号、编组、位置、车辆号、序列号、物料号、WBS、制造商编码/描述和检修商编码按精确值筛选。工厂默认2000可修改，仅用于主数据名称查询。制造商来自生效档案，检修商来自实车记录，不混用两类字段。
- 默认隐藏失效规划、失效位置和作废实车，上车和下车均保留。统一开关重新查询，分别显示三种状态口径。表格内部横向滚动，筛选区自适应排列。
- 查询结果无名称/生效档案时保留行；序列号或物料号缺失时不能点历史。历史展示来源订单类型原值及来源创建时间。
- 编辑档案时序列号/物料号禁改；空制造字段不覆盖。失效档案只提供恢复按钮，恢复请求仅携带状态及版本。管理员保存须检查后端逐条结果，失败保持编辑内容并显示具体原因。
- 分页、导出使用最后提交的查询条件快照；输入框中尚未查询的新条件不改变正在展示数据的导出范围。快速切换查询/历史时只接受最新请求结果，避免旧响应覆盖新行。
- 导出为XLSX，后端同权同范围且最多10000条，超限请缩小条件。无需调用模板的自动部署脚本进行本地验证。

## 上线核对

### 静态部署与Nginx

本仓库Dockerfile现在将 `dist` 内容复制到 `/usr/share/nginx/html/sub/plsm/`，使用根目录 `nginx.conf` 与 `deploy/nginx.conf`。容器内部监听80，外部18090由现有入口服务统一处理；本次不修改现场服务器端口。

若PLSM与主平台由18090上的同一Nginx直接托管：将 `dist` 内的内容放到该站点根目录的 `sub/plsm/` 下，合并 `deploy/nginx.conf` 中 `/sub/plsm`、`/sub/plsm/index.html`、`/sub/plsm/` 三个location（包括内部静态资源规则），保留主平台原有 `/`、其他子应用及 `/api` 代理。**不要将PLSM专用server的 `location / { return 404; }` 或整份nginx.conf覆盖到主平台。** 若站点根目录不是 `/usr/share/nginx/html`，按实际目录对应调整。

若PLSM使用独立静态容器：入口服务器将 `/sub/plsm/` 反向代理到该容器，转发时保留完整 `/sub/plsm/...` URI，不能去掉前缀；入口的 `/api` 继续走现有平台网关。容器只托管静态内容，不将 `/api` 返回为index.html。平台跨域加载静态资源时允许读取，不为API额外放开跨域凭据。

Nginx已经配置页面history回退到 `/sub/plsm/index.html`、入口HTML不缓存、缺失JS/CSS返回404；这样直接刷新功能路径不会误回到主平台首页。静态资源必须与index.html同批发布。

现场保存Nginx配置后先运行 `nginx -t`，通过后再重载。入口原有 `/api/` 代理应转发到实际平台网关并按原规则去除入口代理前缀，确保最终网关收到 `/workplace-plsm/plsm/...`；保持登录、平台菜单等其他服务路由可用，不将整个 `/api/` 都代理到PLSM单个后端。菜单SSE接口 `/api/sys/menu/stream` 应沿用平台的长连接和禁用代理缓冲配置。

执行 `yarn build:production` 生成正式产物；测试环境使用 `yarn build:test`。打包后入口HTML里的资源路径应为 `/sub/plsm/js/...`、`/sub/plsm/css/...`。自动发布脚本现在要求显式设置 `PLSM_DEPLOY_REPOSITORY` 为PLSM专用产物仓库，不再默认推送模板的主应用仓库；本次只提交源码，没有执行发布脚本。

产物发布脚本沿用所配置仓库的默认跟踪分支，不再额外拉取或推送模板master分支；这与本前端源码使用 `plsm` 分支是两件事。平台项目、菜单、角色数据需在内网管理界面按本说明配置，本次没有直接修改现场平台数据。

### 首次验证顺序

1. 先访问 `http://10.151.255.167:18090/sub/plsm/`，检查index及其JS/CSS均成功加载。仅验证静态部署时，不将登录页或首页出现等同于PLSM功能授权已完成。
2. 在主平台选择PLSM项目，分别点击两项菜单；检查页面没有重复出现主平台导航，主平台确实传入当前用户和获准功能。主平台浏览器地址可能由平台路由基座决定，不应自行把项目入口替换成菜单路径。
3. 独立访问下用于检查history回退的路径为 `/sub/plsm/plsmVehicleQuery`、`/sub/plsm/plsmSerialPart`；刷新应返回PLSM入口HTML。真实页面能否打开仍取决于平台登录与菜单权限。
4. 检查请求头 `X-Project-Code: plsm`、认证头及实际API地址；查询/导出/历史请求使用网关路由，不能出现 `/sub/plsm/api`，也不能继续访问模板旧测试地址。
5. 管理员完成档案登记/维护，普通用户验证两页面可查询且无维护按钮；普通用户直接调用保存接口应被拒绝。无项目/角色授权账号不得通过菜单获得访问权限。

先执行后端增量并部署服务，然后建角色菜单、配置真实前缀并部署前端。以管理员、普通用户及无角色账号分别验证页面和直接API调用；核对网关前缀、ResponseResult实际字段、系统账号身份、租户与主数据服务。后端完整步骤见 `../workplace-plsm/docs/V12部署与接口说明_20261111.md`。
